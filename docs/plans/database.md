# Plan: Database and schema for shared records (#6)

## Context

Issue #6 gives every record type in `src/domain/records.ts` a PostgreSQL table and implements the repository interfaces in `src/domain/repositories.ts` (both in PR #1, not merged yet). It is the base for #7 (auth), #10 (capture saves first) and everything after. The stack is confirmed in PR #47: Neon PostgreSQL through the Vercel integration (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, one database branch per preview deploy), Drizzle, PGlite for tests.

## Acceptance criteria (from #6, as testable statements)

- **AC1 Tables.** Every record type has a table; every owned table has a non-null `user_id` and a `version` column.
- **AC2 Same tests.** The PostgreSQL repositories pass one shared repository test suite, which Sihui's in-memory repositories will also run.
- **AC3 Parameterized.** Values are always sent as parameters; input that looks like SQL is stored and read back unchanged.
- **AC4 Config.** The connection string comes from `DATABASE_URL`, listed in `.env.example`; a missing value fails with a clear error; no secret is committed.

## Contract change (PR #1)

`SaveResult` had `saved` and `conflict` (which returns the newer stored record). Two real cases have no stored record to return: updating a record that was deleted meanwhile, and an id that belongs to another user (returning that record would leak it). `{ kind: "not-found" }` was added to `SaveResult` in PR #1 (3af5ed3).

## Design

- **Location.** `src/data/postgres/` for `schema.ts`, `client.ts`, `mappers.ts`, `repositories.ts`. The shared suite lives in `src/data/repository-contract.ts` (a function that registers Vitest tests for any `Repositories` factory). Sihui's in-memory version goes in `src/data/memory/` later. `src/domain/` stays framework-free.
- **Tables.** One per record: users, goals, tasks, time_blocks, fixed_commitments, preferences, temporary_contexts, reminders, messages, open_questions, progress_reports. `id text` primary key (ids are generated by the app). Owned tables have `user_id` referencing `users.id` with cascade delete. Instants are `timestamptz`, `chatDate` is `date`, nested values (availability, quiet hours, check-in times, reminder pause, preferred window) are `jsonb`, `Deadline` is two columns. Union values are `text` typed with Drizzle `$type`. Indexes on `user_id` plus the query columns (time ranges, `scheduled_for`, `chat_date`, `goal_id`); `reminders.delivery_key` unique.
- **Mappers.** Row to record and back, so optional fields come back as missing (not `null`) and instants come back in the domain's ISO UTC string format. Round-trip tests check exact equality.
- **Repositories.** One generic factory for list/get/save/remove, always filtered by `user_id`. `save` rejects a record whose `userId` differs from the caller's (programming error). New record: insert with version 1 if absent. Existing: update where id, user and version match, then version + 1; otherwise return `conflict` with the stored record, or `not-found`. Specialized queries: `listByGoal`, `listOverlapping` (edges that only touch do not overlap, same rule as `recommend-time-block.ts`), `listDue` (pending and due), `listByChatDate`, and `DueReminderSource.listDueForAllUsers` for the reminder job.
- **Drivers.** Production uses `drizzle-orm/neon-serverless` (WebSocket pool, supports transactions for "saved completely or not at all"; Node 22+ has a global WebSocket). Tests use `drizzle-orm/pglite` with migrations applied once per file and tables truncated between tests.
- **Migrations.** `drizzle-kit generate` writes SQL into `drizzle/` (committed, reviewable). A `vercel-build` script runs migrations with `DATABASE_URL_UNPOOLED` and then `next build`, so production and every preview branch are migrated on deploy. Local `npm run build` and CI do not need a database.
- **Versions.** drizzle-orm 0.45.4, drizzle-kit 0.31.11, @neondatabase/serverless 1.2.1, @electric-sql/pglite 0.5.16 (0.6.0 was released on 2026-11-23, too new to adopt).

## Steps (TDD, one commit per phase, evidence in `docs/evidence/05-database/log.txt` with `scripts/tdd-log.sh`)

0. Branch `feat/database` from PR #1's branch (merge `main` into it after #1 merges; rebasing is not allowed in this repository). This plan is the feature plan the TDD workflow asks for.
1. `chore:` setup only: install the four packages, `drizzle.config.ts`, `.env.example` with `DATABASE_URL` and `DATABASE_URL_UNPOOLED` placeholders, `.gitignore` exception `!.env.example`, scripts `db:generate`, `db:migrate`, `vercel-build`.
2. AC1 red/green: test that after migrations each table exists with non-null `user_id` and `version`; then schema and the first migration.
3. AC2 red/green, in small cycles: round trip for every record type; ownership (another user's get, list and remove see nothing); versions (new, stale conflict, not-found); each specialized query. Repository stubs throw "not implemented" so reds fail for missing behavior, not missing code.
4. AC3: SQL-looking strings round-trip unchanged. Drizzle already parameterizes, so this may pass on the first run; if so it is recorded as "not a red step", like the DST test in HW4.
5. AC4 red/green: creating the client without `DATABASE_URL` throws a clear message; `.env.example` lists the variables.
6. Refactor commits where the code repeats.
7. Docs in the same PR: CLAUDE.md layout (`src/data/`) and commands (`db:generate`, `db:migrate`); README getting started note on `.env.local`.
